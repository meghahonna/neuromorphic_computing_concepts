Every organization that buys anything runs this process. An auditor's job is to verify these three documents agree — amounts match, timing makes sense, the vendor is legitimate. When they don't agree, someone has to figure out why.

The problem isn't catching the obvious mismatches. It's the 80% false positive rate — auditors drowning in flags that turn out to be benign, while sophisticated fraud slips through the noise.

I've solved this problem six different ways. Each time I thought I had it figured out, the technology landscape shifted beneath me.

# The entire "intelligence" of the system def three_way_match(po, receipt, invoice): if abs(invoice.amount - po.amount) / po.amount > 0.02: return "FLAG: Amount mismatch" if invoice.date < receipt.date: return "FLAG: Invoice before receipt" if invoice.vendor_id != po.vendor_id: return "FLAG: Vendor mismatch" return "PASS"
✓ What worked

Simple, auditable, explainable to regulators. Runs in milliseconds. Every auditor understands it.

✗ What broke

80% false positives. Misses temporal patterns entirely. Gradual fraud flies under every threshold. Zero learning — same mistakes forever.

🔄

What Invalidated This

Data volumes grew 10x. The false positive flood was unsustainable. I started asking: "Can a model learn what's normal instead of me coding every rule?"

The mental model shifted from "coding rules" to "curating training data." I spent more time labeling historical fraud cases than writing code. The model learned patterns I never would have programmed — vendor seasonality, day-of-week effects, amount clustering.
✓ What worked

Learned patterns from data. FP rate dropped from 80% to ~12%. Could detect gradual inflation, vendor anomalies. Feature importance gave some explainability.

✗ What broke

Needed massive labeled datasets (expensive). Feature engineering was manual and brittle. Couldn't read actual documents — just structured ERP data. New fraud patterns required retraining.

🔄

What Invalidated This

GPT-3 arrived. Then ChatGPT. Suddenly models could understand text — read PO descriptions, parse invoice notes, reason about context. My carefully engineered features felt primitive.

The irony hit me: I was now spending more time on Celery configuration, Redis connection pooling, and rate limit backoff strategies than on the actual fraud detection logic. The "intelligence" was an API call. My job became plumbing.
✓ What worked

Could read and reason about text — PO descriptions, vendor notes, invoice line items. Zero-shot learning meant no training data needed. Explanations were human-readable.

✗ What broke

Slow (seconds per transaction). Expensive at scale. Couldn't see scanned documents — just extracted text. Hallucinations in edge cases. RPM/TPM limits forced complex queuing infrastructure.

🔄

What Invalidated This

GPT-4V launched. Claude got vision. Gemini was multimodal from day one. Suddenly the model could look at the actual invoice PDF. My text extraction pipeline became dead weight.

✓ What worked

✗ What broke

Even slower (images are expensive tokens). Still single-shot analysis — no persistent memory of vendor history. Couldn't maintain state across thousands of transactions. No real-time capability.

🔄

What Invalidated This

Reasoning models arrived — o1, Claude with extended thinking. They didn't just see the documents; they could reason through multi-step verification, use tools, and coordinate sub-tasks. My single-prompt approach became... quaint.

And then I saw the Kimi K2 paper. Agent swarm patterns within the model itself — not orchestrated by my code, but emerging from the model's architecture. My hand-crafted sub-agent topology was already becoming an artifact of a brief window where we had to build the scaffolding ourselves.
✓ What worked

Deep investigation capability. Each sub-agent specializes. Can query external systems, reason multi-step, and explain its chain of thought. Catches complex schemes.

✗ What broke

Extremely slow (minutes per investigation). Expensive. Non-deterministic. Agent orchestration is fragile. Not suitable for real-time, continuous monitoring. Can't process 10,000 transactions/day economically.

🔄

The Question That Changed Everything

What if the computation itself was temporal? What if instead of batch-processing documents, the system was always-on — processing events as they happen, building memory, learning in real-time, consuming near-zero power between events? That's when I discovered neuromorphic computing.

Why This Is Different

Every previous approach processed transactions as isolated snapshots. The neuromorphic approach treats the entire procure-to-pay lifecycle as a temporal stream. The SNN builds an internal model of each vendor's "rhythm" and fires when something breaks the pattern.

Gradual inflation over months? The membrane potential slowly builds. Phantom vendor with no baseline? Maximum firing from day one. Invoice before receipt? The temporal ordering of spikes is literally reversed — the network detects this natively.

The pattern is clear: every 12-18 months, a capability emerges that doesn't just improve the previous solution — it invalidates the architecture. The question isn't whether the next wave will come. It's whether you'll recognize it fast enough to ride it instead of being swept away.

The Real Lesson

The technology you master today will be a footnote in 18 months. That's not a threat — it's a liberation. Stop optimizing for the current paradigm and start building the muscle to recognize paradigm shifts.

When text LLMs emerged, the winners weren't the best ML engineers — they were the ones who realized the game had changed. When vision arrived, the winners weren't the best prompt engineers — they were the ones who deleted their OCR pipelines without hesitation.

Right now, neuromorphic computing is where deep learning was in 2015 — early, impractical for most, but carrying a signal about the future. The question for you isn't "should I learn snnTorch." It's: "What architectural assumption am I making today that will be invalidated by a capability I haven't imagined yet?"
